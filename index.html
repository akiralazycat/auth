ACCOUNT & IDENTITY DESIGN

Authentication should protect the person, not just the login form.

A compact design guide for Passkeys, external providers, recovery, sessions, and sensitive account actions. The goal is simple: make strong account security easier to reason about, easier to maintain, and easier for users to understand.

Read the principles See the action matrix

Open design, isolated implementation. Share security contracts and proven helpers. Keep product databases, secrets, OAuth clients, Passkey configuration, and session keys separate unless centralization is deliberate.

01

Identity is not email

External identities should be keyed by provider and immutable subject. Matching email addresses are not a safe automatic merge rule.

02

Recovery is constrained

A recovery link should restore a path to control, not silently mint a fully privileged account session.

03

Proof should match risk

Routine access, credential changes, and destructive authentication-root actions should not all require the same assurance.

PRINCIPLES

Twelve rules for a calmer security model.

These are behavioral contracts, not framework choices. They should survive changes in UI, database, hosting, and client platform.

01

Identity is not email.

Use provider + immutable subject for external identity. Treat provider email as metadata, not a merge key.

02

Login, linking, and reauthentication are different ceremonies.

Bind each flow to an explicit intent, expected session, provider, expiry, and safe return path.

03

Sensitive actions deserve fresh proof.

An old browser session should not automatically authorize credential or recovery changes.

04

Never let the user strand themselves.

The server should reject any mutation that leaves zero usable sign-in methods.

05

Availability is not independence.

Multiple synchronized Passkeys improve resilience but may still share one upstream trust root.

06

Recovery is a constrained state transition.

Use a restricted recovery session until sufficient assurance has been rebuilt.

07

Recovery email is not a master key.

Inbox access alone should not silently satisfy the strongest destructive-action requirements.

08

Sessions have purpose.

Normal, temporary shared-device, recovery, and native sessions should carry explicit capabilities and lifetimes.

09

Active sessions and history are different data.

Separate authoritative current access from historical security events.

10

Security should be legible.

Show users what can sign in, what is active, what changed, and why stronger proof is required.

11

Web and native share policy.

Transport can differ. Assurance, recovery, credential, and revocation semantics should not.

12

Share policy; isolate blast radius.

Reuse stable contracts and helpers while keeping product credentials, databases, and cryptographic material isolated.

ASSURANCE

Three levels are enough to make intent explicit.

The labels matter less than the discipline: distinguish an active session, a fresh proof, and independent proof families.

A0

Active session

Allowed current session is sufficient for low-risk operations.

  • Example: revoke one other active device
A1

Fresh proof

One recent credential proof. A ten-minute freshness window is a practical starting point.

  • Add or remove one credential
  • Link or unlink a provider
  • Change recovery email
A2

Independent proofs

Two eligible proof families for destructive authentication-root changes.

  • Remove all Passkeys
  • Delete the account
  • Release a scarce identity root

RECOVERY & SESSIONS

Recovery should rebuild control without creating a shortcut around security.

RECOVERY

Restricted first, normal later.

ARCHITECTURE

Share the contract. Keep the failure domains deliberate.

Common policy reduces drift. Isolation prevents one product compromise from automatically becoming every product compromise.

GOOD TO SHARE

  • Credential semantics
  • OAuth intent model
  • Step-up policy
  • Recovery lifecycle helpers
  • Session-kind semantics
  • Security-event vocabulary
  • Conformance fixtures

KEEP ISOLATED

  • Account databases
  • OAuth secrets and private keys
  • Passkey RP configuration
  • Session and encryption keys
  • Cookie domains
  • Product migrations
  • Product-specific identity rows

REVIEW CHECKLIST

Before calling an auth flow finished.

Does external identity use immutable provider subject?

Can a callback distinguish login, link, and reauth?

Can the last usable sign-in method be removed?

Do sensitive actions require fresh proof?

Are destructive root changes stronger than routine settings?

Does recovery create a restricted state first?

Can temporary sessions mutate credentials?

Are active sessions distinct from audit history?

Does native preserve the same action policy?

Are secrets and relying-party configuration isolated per product?
